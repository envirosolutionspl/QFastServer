# QFastServer 3.44.15-qfs.1 and QJazz

[QJazz](https://github.com/3liz/qjazz) (3Liz) is a server for QGIS Server used in the Lizmap stack: an HTTP
front written in Rust passes the requests over gRPC to a pool of Python processes, each of which loads QGIS
Server as a library. It replaces the FastCGI front of the official image, so it was measured against
QFastServer as well, and also with the QGIS libraries of QFastServer in place of its own.

Measured on 2026-11-13 (vector maps and other services) and 2026-11-15 (all other families). Every cell of
the tables is in [3.44.15-qfs.1-qjazz.csv](3.44.15-qfs.1-qjazz.csv). The method, the data and the requests are
those of [3.44.15-qfs.1.md](3.44.15-qfs.1.md).

## Summary

62 kinds of requests, four variants, every family of requests measured with all four variants in one session.

- **QFastServer against QJazz**: the median response time with one client is lower for 62 of the 62 kinds of
  requests (geometric mean of the ratio: QJazz 1.67 times slower), the throughput with 16 clients is higher
  for 43 of 44 (geometric mean: 1.47). The one exception is GetFeatureInfo as GML, 743 against 759 requests
  per second, within the noise.
- **QJazz against the official QGIS Server image**: QJazz does not have the floor of about 11 ms which the
  FastCGI front of the official image adds to every request. Light requests (GetCapabilities, GetFeatureInfo,
  the legend, raster tiles as JPEG) are 2 to 6 times faster. Rendering is not: maps of 1024x768 pixels take the
  same time or longer. Lower median for 31 of 62 kinds of requests, higher throughput for 26 of 44.
- **WFS GetFeature is 3 to 4 times slower with QJazz** than with either FastCGI image (GML 158 ms against 49
  and 41 ms, GeoJSON 84 ms against 21 and 24 ms). The QGIS libraries of QFastServer do not change this (112 and
  84 ms), so the time is spent outside QGIS; the cause was not investigated.
- **The QGIS libraries of QFastServer work under QJazz.** Put into the QJazz image, they give responses
  identical byte for byte to those of QFastServer and make QJazz faster: median 1.44 times lower, throughput
  1.31 times higher on average, lower median for 61 of 62 kinds of requests. The largest gains are for rasters
  (1.74) and vector maps (1.63).
- **QJazz with the libraries of QFastServer is slower than QFastServer** by 16% on average in the median (about
  1 to 3 ms more for each request) and by about 11% in throughput.

So the gains of QFastServer come from two independent sources. The removal of the FastCGI floor is something
QJazz achieves with its own front. The faster rendering and encoding (PNG, rasters, reprojection, 8 bits PNG,
GetFeatureInfo, GML) is in the QGIS libraries of QFastServer and works under QJazz as well.

These numbers come from one machine. Differences below about 10% are not resolved by this set-up.

## Servers

| Variant | Image | Front and processes |
| --- | --- | --- |
| QGIS Server | `qgis/qgis-server:3.44.15-noble` | nginx of the image, 4 FastCGI processes |
| QFastServer | `ghcr.io/envirosolutionspl/qfastserver:3.44.15-qfs.1` | as above |
| QJazz | `3liz/qjazz:qgis-3.44.15-0.10.0` (Ubuntu 24.04, qgis.org packages `1:3.44.15+40noble`, the same QGIS as the official image) | `qjazz-map` and `qjazz-rpc`, 4 QGIS processes |
| QJazz with the libraries of QFastServer | built from the QJazz image, see below | as QJazz |

All four: 4 CPUs and 4 GB of memory for the container, 4 QGIS processes, parallel rendering off, the same
projects and the same PostGIS database.

QJazz runs with the defaults of its image apart from the number of processes. The front and the pool run in
one container, so that the limits cover the whole server as they do for the other images:

```bash
CONF_WORKER__NAME=bench \
CONF_WORKER__NUM_PROCESSES=4 \
CONF_WORKER__QGIS__PROJECTS__SEARCH_PATHS='{"/": "/project"}' \
CONF_WORKER__QGIS__PROJECTS__TRUST_LAYER_METADATA=false \
CONF_WORKER__QGIS__PROJECTS__DISABLE_GETPRINT=false \
  qjazz-rpc serve &
CONF_BACKENDS__BENCH__HOST=localhost CONF_BACKENDS__BENCH__ROUTE=/ exec qjazz-map serve
```

The project is chosen with the `MAP` parameter of the request. For the project with trusted layer metadata
the two `PROJECTS` settings are `true`, as `QGIS_SERVER_TRUST_LAYER_METADATA` and
`QGIS_SERVER_DISABLE_GETPRINT` are for the FastCGI images.

QJazz with the libraries of QFastServer: the QJazz image with the QGIS files replaced by those of the
QFastServer image of the same version.

```dockerfile
FROM ghcr.io/envirosolutionspl/qfastserver:3.44.15-qfs.1 AS qfs
FROM 3liz/qjazz:qgis-3.44.15-0.10.0
USER root
RUN --mount=type=bind,from=qfs,source=/usr,target=/qfs \
    rm -rf /usr/lib/qgis && cp -a /qfs/lib/qgis /usr/lib/qgis \
 && cp -a /qfs/lib/libqgis_* /usr/lib/ \
 && cp -a /qfs/lib/python3/dist-packages/qgis/. /usr/lib/python3/dist-packages/qgis/ \
 && cp -a /qfs/share/qgis/. /usr/share/qgis/ \
 && ldconfig
USER qgis
```

Checked before the measurement: no QGIS library of the QJazz image is left without a replacement, `ldd`
reports no missing library, `qgis.core`, `qgis.server` and `qgis.analysis` import. A GetMap response of QJazz
is identical byte for byte to that of the official image; with the libraries of QFastServer it is identical to
that of QFastServer. This image is not published; it was built only for this measurement.

## Method

As in [3.44.15-qfs.1.md](3.44.15-qfs.1.md): k6 1.8.2, closed loop, a warm-up of 10 s with 4 clients, then
20 s with 1 and with 16 clients (output formats: 1 client only); one server at a time, each started from
scratch before a family of requests.

The same machine was 5 to 28% slower on 2026-11-13 than on 2026-11-11 with the same images, so the official
image and QFastServer were measured again next to QJazz. Compare the numbers of this document with each other,
not with those of [3.44.15-qfs.1.md](3.44.15-qfs.1.md).

| Session | Families |
| --- | --- |
| 2026-11-13 | vector maps, other services |
| 2026-11-15 | project with 200 layers, reprojection, raster, cascaded WMS, output formats |

Mains power was checked before every start of a server. A first attempt of the second group of families on
2026-11-13 was discarded: the machine went to sleep during the run.

Cells: **median response time with one client in ms / requests per second with 16 clients**. Median only where
the request was measured with one client.

## What to keep in mind

- QJazz was run with its front and its pool in one container limited to 4 CPUs, with the defaults of the image
  apart from the number of processes. Deployments of QJazz usually run the front and the pool separately and
  may set other limits, another number of processes, another size of the gRPC chunks (1 MiB by default) or
  timeouts. Other settings may give other results, above all for WFS and for the throughput with 16 clients,
  where the front and the QGIS processes share the same 4 CPUs.
- The comparison between QJazz and QJazz with the libraries of QFastServer does not depend on these settings:
  the front, the pool and the settings are the same, only the QGIS libraries differ.
- Failed responses: 14 responses of the 8 bits PNG map of buildings, spread over all four variants (4, 3, 2
  and 5), failed the minimum size check of 4000 bytes; these are nearly empty images, not server errors. No
  other failed response.
- One machine; the load generator and the database run on it as well.

Not measured with QJazz: GetPrint, DXF, WCS; the front and the pool in separate containers; other settings of
QJazz; the cause of the slow WFS GetFeature.
