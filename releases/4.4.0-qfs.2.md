Second release of QFastServer for QGIS Server 4.4.0: the variable `QT_NO_GUI_THREADPOOL` of Qt now takes
effect in the FastCGI server, which makes GetPrint PNG and other large renderings faster when several QGIS
Server processes share the CPUs.

```bash
docker pull ghcr.io/envirosolutionspl/qfastserver:4.4.0-qfs.2
```

Use the image exactly as `qgis/qgis-server:4.4.0-resolute`: same ports, volumes and environment variables.
Without the options `QFASTSERVER_WORKERS` and `QFASTSERVER_GZIP` the container is started by the unchanged
start script of the official image. `QT_NO_GUI_THREADPOOL` is not set by default.

## Verification

- Responses of the image compared with the official image `qgis/qgis-server:4.4.0-resolute`, 59 request types,
  both with 4 processes. Without `QT_NO_GUI_THREADPOOL`: 54 of 59 identical. With `QT_NO_GUI_THREADPOOL=1`, two
  passes: 54 and 55 of 59. The others (8 bits PNG, PDF, DXF, a cascaded WMS layer) also differ between two
  processes of the official image itself. GetPrint PNG is identical in every pass.
- Thread switches of the QGIS Server processes for one GetPrint PNG: about 920 without the variable (as with
  the release 4.4.0-qfs.1), 31 with it.
- Upstream tests on the patched build with `QT_NO_GUI_THREADPOOL=1`, at the tag `final-4_4_0`: layouts,
  GetPrint, labeling in layouts, map renderer jobs and render context, 62 of 62 that do not need PostgreSQL.
  The suites run for 4.4.0-qfs.1 were not run again: the new patch changes the start of `qgis_mapserv` only.

## Performance

This image without `QT_NO_GUI_THREADPOOL` against the same image with `QT_NO_GUI_THREADPOOL=1`, both with 4
QGIS Server processes, 4 CPUs and 4 GB per container, PostGIS on the same host. Each cell runs 15 s; the two
alternate in the order without, with, with, without, and the result is the mean of the two passes.

| Request | Median, 1 client | Requests/s, 16 clients |
| --- | --- | --- |
| GetPrint, PNG (A4, 100 DPI) | 89.7 → 73.6 ms | 22.1 → 30.9 |
| GetPrint, PDF | 47.1 → 52.3 ms | 25.0 → 20.8 |
| GetLegendGraphic, PNG | 4.0 → 4.5 ms | 766 → 660 |
| GetFeatureInfo, XML | 3.2 → 3.9 ms | 938 → 839 |
| WMTS GetTile | 5.7 → 5.8 ms | 333 → 332 |
| GetMap, 8 bits PNG | 35.5 → 35.9 ms | 47.0 → 47.2 |
| Tile 256x256, 1 vector layer, PNG | 5.3 → 4.7 ms | 427 → 404 |
| Tile 256x256, 3 vector layers, PNG | 8.2 → 8.7 ms | 244 → 226 |
| Map 1024x768, 1 vector layer, PNG | 16.4 → 15.6 ms | 94 → 90 |
| Map 1024x768, 3 vector layers, PNG | 28.4 → 25.6 ms | 55 → 57 |

GetPrint, GetLegendGraphic and GetFeatureInfo were measured again in the reverse order (with, without,
without, with): GetPrint PDF 46.6 → 43.7 ms and 23.8 → 24.6 requests/s, GetFeatureInfo 3.2 → 3.2 ms and
1031 → 986 requests/s, GetLegendGraphic 3.8 → 4.0 ms and 811 → 771 requests/s. Only GetPrint PNG is clearly
faster; GetLegendGraphic PNG is 5 to 15% slower in both orders (0.2 to 0.5 ms); the other differences go one
way in one order and the other way in the other, within what this set-up resolves.

Machine: Intel Core Ultra 7 165H (16 cores, 22 threads), Docker Engine 29.9 on WSL 2 with 22 CPUs and 16 GB,
laptop on mains power.

## Changes since 4.4.0-qfs.1

- Patch 0016: Qt reads `QT_NO_GUI_THREADPOOL` when its GUI thread pool is first used. In `qgis_mapserv` that
  was during the first request, after `FCGI_Accept()` had replaced the environment of the process with the
  parameters of the request, so the variable was never seen. When the variable is set, the pool is now used
  once before the first request. Without the variable nothing changes.

See the [README](https://github.com/envirosolutionspl/QFastServer#options-of-the-image) for when to set it.

## Known differences from upstream

- PNG files of vector maps are smaller; PNG files of pure imagery are about 20% larger (rows are written
  without the filter search).
- The image is built with the options of the upstream Debian packaging, without the desktop application and
  the GRASS plugins, which the official server image does not contain either. The landing page web
  application of the official image is kept.
- The command of the image is another script, which runs the one of the official image.
- With `QT_NO_GUI_THREADPOOL` set, the variable reaches QGIS Server; in the official image it has no effect.

## Not verified

- A single large print (A3 or A0 at 300 DPI) on a machine with idle CPUs, which can be slower without the
  thread pool.
- Python server plugins (for example `lizmap_server`) with this image.
- WFS transactions, GetPrint with an atlas, GeoPDF.
