# Benchmark of QFastServer 3.44.15-qfs.1

QFastServer against the official QGIS Server image of the same version, MapServer and GeoServer.
Measured on 2026-11-11 with the published image `ghcr.io/envirosolutionspl/qfastserver:3.44.15-qfs.1`.
Every cell of the tables is in [3.44.15-qfs.1.csv](3.44.15-qfs.1.csv).

## Summary

52 kinds of requests, 478 runs of 20 s.

- **Against the official QGIS Server image**: the median response time with one client is lower for 49 of
  the 52 kinds of requests (geometric mean of the ratio: 0.53), the throughput with 16 clients is higher for
  36 of 38 (geometric mean: 1.59). Four cells came out 6 to 9% worse in this run; a separate run with the two images alternating did not confirm a regression (see below).
- **Against MapServer**: lower median for 45 of 50 kinds of requests, higher throughput for 31 of 36.
  MapServer is clearly faster for WFS GetFeature as GML and slightly faster for a map of a reprojected raster
  as JPEG.
- **Against GeoServer**: lower median for 33 of 51, higher throughput for 29 of 37. GeoServer is faster with
  one client for vector maps of 1024x768 pixels (by 4 to 10%), for WFS and for the legend, and it has the
  highest throughput for tiles of a cascaded WMS layer. It is several times slower for rasters and for the
  reprojection to EPSG:2180, and its throughput with 16 clients falls below its throughput with 4 clients.
- The official QGIS Server image never answers faster than about 10.8 ms with one client, not even a cached
  GetCapabilities document. QFastServer answers the same request in 0.9 ms.

These numbers come from one machine and one run. Differences below about 10% are not resolved by this set-up.
The other servers were not tuned beyond what is described below; read their columns as "the image as it
comes, with the same resources", not as the best they can do.

## Servers

| Server | Image | Front and workers |
| --- | --- | --- |
| QGIS Server 3.44.15 | `qgis/qgis-server:3.44.15-noble` | nginx of the image, 4 FastCGI workers |
| QFastServer 3.44.15-qfs.1 | `ghcr.io/envirosolutionspl/qfastserver:3.44.15-qfs.1` | the same |
| MapServer 8.6.6 | `camptocamp/mapserver:8.6` | lighttpd of the image, 4 FastCGI workers |
| GeoServer 3.0.2 | `geosolutionsit/geoserver:3.0.2` (Tomcat 11, JDK 21) | the Java server of the image, 2 GB of heap |

- The container of the server under test has 4 CPUs and 4 GB of memory. One server runs at a time.
- PostGIS 16 (`postgis/postgis:16-3.5`) runs in another container without a CPU limit.
- QGIS Server and QFastServer use the same projects and the same environment; parallel rendering is off and
  the 4 workers are started in advance (the image starts one by default).
- MapServer: 4 workers started in advance, database connections kept between requests.
- GeoServer: the configuration of the image, only the heap size is set. Its tile cache takes no part in the
  WMS measurements.
- The styles were written by hand for every server. The images are not identical between the servers; the
  response sizes are in the data file.

Data: an OpenStreetMap extract of one Polish region in PostGIS in EPSG:3857 (530,813 buildings, 62,333 land
use polygons, 127,421 roads, 1,131 places with labels); a Sentinel-2 true colour image of 10980x10980 pixels
in EPSG:32633 as a deflate compressed GeoTIFF with overviews; a WMS layer served by a second MapServer for
the cascading; a project with 200 layers (the 4 layers and 196 views of the same tables).

## Method

- k6 1.8.2, closed loop: every client sends its next request when the response has arrived.
- Every cell: 10 s of warm-up with 4 clients, then 20 s of measurement, with 1 and with 16 clients.
- The requests come from one random list which is the same for every server: tiles of 256x256 and maps of
  1024x768 pixels at several scales; the same boxes and limits for the other services (GetFeatureInfo up to
  10 features, WFS up to 2000 features).
- Every response is checked: status 200, content type, smallest plausible size.
- Cells of the tables: **median response time with 1 client in ms / requests per second with 16 clients**.
  Only the median where the request was measured with one client only.

Not applicable: GetFeatureInfo as JSON for MapServer (GeoJSON only for one queried layer); WMTS for MapServer
(a separate product) and for GeoServer (it serves tiles from its cache, which would not measure rendering);
GetPrint (no counterpart in the other servers, and QFastServer does not differ from QGIS Server there).

## Requests where QFastServer came out slower than QGIS Server

Four cells of the main run were worse for QFastServer than for the official image. Three of them were
measured again: the two images alternating in the order A B B A, 20 s each, mean of the two runs of an image.

| Request | Main run, QGIS Server → QFastServer | Alternating run, QGIS Server → QFastServer |
| --- | --- | --- |
| Tile, raster under 3 vector layers, PNG: median, 1 client | 15.3 → 14.3 ms | 15.9 → 10.1 ms |
| Tile, raster under 3 vector layers, PNG: requests/s, 16 clients | 180 → 164 | 192 → 248 |
| Map, 3 layers, JPEG: median, 1 client | 17.7 → 19.3 ms | 20.1 → 19.6 ms |
| WFS GetFeature, GeoJSON: median, 1 client | 16.7 → 18.0 ms | 17.1 → 18.0 ms |
| WFS GetFeature, GeoJSON: requests/s, 16 clients | 161 → 159 | 151 → 149 |
| Map, buildings, 8 bits PNG: median, 1 client | 18.6 → 19.6 ms | not measured again |

- Tile of the raster under vector layers: the value of QFastServer in the main run was an outlier. The tables
  above keep the values of the main run.
- Map as JPEG: no difference. The official image alone gave 17.7 ms in the main run and 20.1 ms in the
  alternating run, which shows the spread of this method.
- WFS as GeoJSON: the median of QFastServer is about 5% higher in both pairs of runs, its mean response time
  is 6% lower (47.7 → 50.7 requests/s with one client), the throughput with 16 clients is the same. No patch
  touches the GeoJSON writer; the cause of the shift of the median was not investigated.
- 8 bits PNG: the alternating script does not send that format. In-process, 24 different maps take 11% less
  time with the patches; under load the difference is within the noise.

## Failed responses

- GeoServer, reprojected raster as JPEG with 16 clients: 7 of 171 maps and 1 of 1408 tiles were a service
  exception instead of an image.
- 8 bits PNG, map of the buildings: 6 responses each of QGIS Server, QFastServer and MapServer were counted as
  failed by the size check. They are correct images smaller than the limit of the check (3.2 kB against
  4 kB), for the same requests on the three servers; the limit was too high for palette images.
- No failed response in any other run.

## What to keep in mind

- One machine (a laptop with a hybrid processor), one run of 20 s for each cell, the load generator on the
  same processor. Differences below about 10% are not resolved.
- The front differs between the servers (nginx, lighttpd, the Java server); its cost is part of the result.
- The response sizes differ for the same content: the GML of GeoServer is about half the size of the GML of
  QGIS (675 kB against 1.24 MB), the WMS capabilities of GeoServer are 550 kB (QGIS 13.5 kB, MapServer 12 kB).
- The legend of GeoServer is 199 bytes (a style without rule titles), the legend of QGIS 4 to 5 kB: that row
  does not compare the same work.
- 8 bits PNG: every server reduces the colours with its own algorithm. GeoServer is sent `FORMAT=image/png8`,
  because it answers `image/png; mode=8bit` in RGB.
- Cascading: the source MapServer runs on the same machine and needs 8 ms for a tile and 35 ms for a map on
  its own; the cascading rows include that time.
- GeoServer was not tuned. Its results for rasters and for EPSG:2180 may come from the defaults of the image
  and not from the server itself; this was not investigated.
- The data is one region with simple styles (fills, lines, point labels). Projects with rule based
  symbology, expressions, complex labels or other data sources may give other proportions.

Not measured: GetPrint, WCS, OGC API Features and WFS transactions between the servers; more than 16 clients;
mixed load; runs of several hours; another machine.

## Data file

[3.44.15-qfs.1.csv](3.44.15-qfs.1.csv): one line for each run, times in ms.

- `variant`: the server and its project. `qgis*` is the official QGIS Server image, `qfs*` QFastServer;
  `_l` the project with 200 layers, `_l_trust` the same with trusted layer metadata, `_ext` the project with
  the rasters and the cascaded layer, `_svc` the project with WFS and WMTS published; `upstream` is the
  MapServer which is the source of the cascaded layer.
- `scenario`: the layers (`S1` buildings, `S2` roads, `S3` land use, buildings and roads, `S4` the same with
  labelled places, `L1` and `L10` 1 and 10 layers of the project with 200 layers, `R` the raster, `RB` the
  raster with bilinear resampling, `R3` the raster under 3 vector layers, `C` the cascaded layer, `C3` the
  cascaded layer under roads), then the CRS and the format of the request. `V.*` are the other services.
- `size`: `tile` 256x256, `map` 1024x768 pixels. `concurrency`: number of clients.
- `errors`: responses which failed a check; see the section on failed responses.
