Second release of QFastServer for QGIS Server 3.44.15: empty maps are written as compact PNG files, and the
image can start several QGIS Server processes.

```bash
docker pull ghcr.io/envirosolutionspl/qfastserver:3.44.15-qfs.2
```

Use the image exactly as `qgis/qgis-server:3.44.15-noble`: same ports, volumes and environment variables.
Without the two new options the container is started by the unchanged start script of the official image.

## Verification

- Responses compared with the official image `qgis/qgis-server:3.44.15-noble`, 59 request types, both images
  started with their defaults (one process), four passes: 55 of 59 identical in each pass. The four others
  (GetContext, 8 bits PNG, DXF, PDF) also differ between two processes of the official image itself, which
  compared with itself gave 56 of 59.
- PNG maps compared with the release 3.44.15-qfs.1, 10 kinds of maps: the decoded pixels are the same for all
  of them; the files of the maps which are not nearly empty are the same byte for byte.
- Upstream tests of the server: 56 of 56, the three which need PostgreSQL included. They were run with the
  same patches on the branch `release-3_44` 28 commits after the tag `final-3_44_15`, not on the tag itself.
  The suites for rasters, projects, vector layers and DXF were not run again: the new patch changes the PNG
  writer of the WMS service only. The 68 raster renderings were not compared again for the same reason.
- Start of the image: with the defaults, the same processes as the official image. With
  `QFASTSERVER_WORKERS` the number of processes asked for, also together with `SKIP_NGINX`,
  `NGINX_CORS_ALLOW_ORIGIN` and `QGIS_SERVER_LANDING_PAGE_PREFIX` of the official image; the container stops
  when one of the processes ends. With `QFASTSERVER_GZIP` a GetCapabilities document is the same after
  decompression.

| Empty, white background, 1920x1080 | 38677 → 9995 bytes | 32.7 → 33.7 ms |

## Changes since the previous release

- Patch 0015: 32 bits PNG images which are empty or nearly empty are deflated with the run-length strategy
  of zlib. In 3.44.15-qfs.1 an empty map took about 4.5 times the room it takes with the official image.
- `QFASTSERVER_WORKERS`: number of QGIS Server processes of the container. Default 1, as the official image.
- `QFASTSERVER_GZIP`: compression of the XML, JSON and text responses by the nginx of the image. Off by
  default, as in the official image.
- The command of the image is now `/usr/local/bin/qfastserver-start.sh`. It applies the two options and
  then runs `/usr/local/bin/start-xvfb-nginx.sh`, the start script of the official image, which is not
  changed. A deployment which calls that script itself keeps working, without the two options.

See the [README](https://github.com/envirosolutionspl/QFastServer#options-of-the-image) for the options and
[UPSTREAM.md](https://github.com/envirosolutionspl/QFastServer/blob/main/UPSTREAM.md) for the patches.

## Known differences from upstream

- PNG files of vector maps are smaller; PNG files of pure imagery are about 20% larger (rows are written
  without the filter search).
- The image is built with the options of the upstream Debian packaging, without the desktop application and
  the GRASS plugins, which the official server image does not contain either.
- The command of the image is another script, which runs the one of the official image.

## Not verified

- Python server plugins (for example `lizmap_server`) with this image.
- WFS transactions, GetPrint with an atlas, GeoPDF.
- The memory used by several processes with large projects, and `QFASTSERVER_WORKERS` under a load test.
